# 개발 Oracle 기반 모바일인증 검증 절차

## 1. 검증 기준과 현재 구현 범위

최종 검증 환경은 **사내 개발단말 + 개발 Oracle 19c의 기존 SMS 스키마/테이블**이다.
별도 스키마나 Docker를 필수로 요구하지 않는다. 기존 SQL의 `SMS.` 소유자 표기도 유지한다.
로컬 Docker 시험은 결함 재현·회귀 확인용이며 개발 환경의 네트워크·권한·DDL·성능 검증을 대체하지 않는다.

애플리케이션 빌드와 격리 JUnit은 [Java 8/21 선택 빌드 안내](dual-jdk-build.md)에 따라 두 버전에서 실행할 수 있다. 이 문서의 개발 Oracle 사전 점검 도구는 여전히 JDK 21과 java21 프로파일의 ojdbc11을 사용한다.

이 문서는 현재 실행 가능한 도구와 다음 구현 항목을 구분한다. 아직 없는 전체 인증·부하 명령을 실행 가능한 명령처럼 제공하지 않는다.

| 항목 | 상태 | 실제 검증 범위 |
|---|---|---|
| `verify-mobilecert.sh` | 기존 구현 | JUnit, 전문 바이트, 기동, Hikari/소켓의 격리 시험 |
| `verify-oracle.sh` | 기존 구현, Docker 전용 | 임시 로컬 PDB의 DAO 시험. 개발 DB에 전용하지 않음 |
| `verify-dev-oracle.sh` | 이번 추가 | 개발 DB 설정 검사와 읽기 전용 접속·객체 사전 점검 |
| 실제 서버 + MCI 클라이언트 + 상태 있는 KCB 모의 서버 | 다음 구현 | 정상 STEP1/STEP2, 최종 응답·DB 결과·외부 호출 수 대조 |
| 전체 인증 장애·부하 실행기 | 다음 구현 | 아래 허용 범위의 장애·동시성·자원 회수 검증 |
| 운영 코드 로그 정비 | `safe-logging` 구현 후 메인 통합 완료, 회귀·coverage 검증 완료 | 레벨 API·민감값 출력 제거·요청 ID·정제된 예외. [구현과 제한](logging-improvement.md) 참조 |

**사전 점검 PASS는 인증 성공, INSERT/UPDATE 권한, 실제 DAO 실행, Hikari 동작, 처리량 검증을 뜻하지 않는다.**
새 점검기는 실제 ojdbc11로 접속하지만 DBFactory/Hikari 또는 인증 서버를 기동하지 않는다.

## 2. 기존 SMS 스키마를 사용하는 범위

공용 개발 DB에는 가상 DDL이나 실패 유도용 제약조건을 배포하지 않는다. 새 쉘은 DDL/DML, 시퀀스 NEXTVAL, KCB/MCI 호출을 수행하지 않는다.

전체 인증 테스트를 추가할 때에는 기존 월별 테이블·부서 정보·시퀀스를 그대로 사용한다. 테스트용으로 합의한 합성 입력과 실행별 관리 목록으로 생성된 거래를 구분한다. 이름·전화번호의 특정 문자열만 보고 삭제 대상을 정하면 안 된다.

| 구분 | 공용 개발 SMS에서의 방식 |
|---|---|
| 접속·DB 식별·필요 컬럼 조회 | 읽기 전용 사전 점검 |
| 정상 인증 요청·결과 저장 | 합성 입력으로 실제 서비스 실행. 쓰기 발생을 명시하고 해당 실행의 거래 추적 |
| 인증번호 오류·만료 등 | 테스트 거래와 모의 KCB 응답으로 검증 |
| KCB 지연·분할 응답·연결 종료 | 로컬 모의 서버에서 재현. DB에 장애를 만들지 않음 |
| 풀 대기·부족 | 별도 테스트 JVM의 작은 풀로 제한된 검증. DB 세션 고갈 유발 금지 |
| SQL 실패·두 번째 INSERT 실패·DB 중단 | 격리 JUnit/로컬 Oracle에서 재현. 공용 DB 제약조건·권한·세션을 변경하지 않음 |
| 데이터 정리 | 보관 정책에 따라 실행별 확정 키만 검토. 기본 자동 삭제 없음 |
| 성능 부하 | DB 영향 범위·시간·중단 기준을 정한 별도 작업. 기본 접속 점검에 포함하지 않음 |

별도 스키마를 제안했던 이유는 장애 주입·삭제의 격리였다. **정상 개발 통합 시험을 위해 기존 SMS를 복제할 필요는 없다.**

## 3. Vault 도입 전 접속정보 취급

사내에서 이미 승인된 DB 접속 방식이 있으면 그 방식을 따른다. 아래 방식은 당장의 대화형 사전 점검용이며 보안 정책 적합성을 도구만으로 보증하지 않는다.

1. DBA가 부여한 개발 전용 계정으로 실행한다. 이 점검에 SYS/SYSTEM/DBA 권한은 필요 없다. 가능한 경우 필요한 객체 조회 권한만 사용한다. 스키마 이름이 SMS라고 로그인 계정도 반드시 SMS일 필요는 없다.
2. DB 주소·예상 DB 식별값·대상 테이블명은 저장소 밖의 개인 디렉터리(0700), JSON 파일(0600)에 보관한다. 이 파일에도 계정/비밀번호 필드는 허용하지 않는다.
3. 계정과 비밀번호는 실행할 때 터미널에서 숨김 입력한다. 명령행 인자, `-D...`, `export PASSWORD=...`, `.env`, 서비스 XML, Git, 보고서에 적지 않는다.
4. Python이 입력값을 Java 표준입력 파이프로 전달한다. 쉘은 JSON을 `source`/`eval`하지 않는다. 터미널 숨김 입력이 불가능하면 평문 입력으로 전환하지 않고 실패한다.
5. 연결 시 Oracle 네이티브 네트워크 암호화와 무결성 검사를 `REQUIRED`로 요청한다. 협상 실패 시 평문 접속으로 재시도하지 않는다. DBA와 해당 정책을 맞춘다. Oracle JDBC는 이런 연결 속성을 지원한다. [Oracle 19c JDBC 보안 문서](https://docs.oracle.com/en/database/oracle/oracle-database/19/jjdbc/client-side-security.html)
6. 원문 JDBC 오류·SQL·주소·계정은 출력하지 않는다. 고정 실패 코드·정규화한 SQLState·Oracle 오류번호만 결과에 남긴다.

현재 도구는 단순 `jdbc:oracle:thin:@//host:port/service` 형태만 지원한다. TCPS 인증서/Wallet/TNS 별칭이 사내 필수 방식이면 그 설정을 별도로 구현해야 하며 보안 설정을 낮춰 우회하지 않는다. 네이티브 암호화 요구는 TCPS의 인증서 기반 서버 신원 검증을 대신한다는 뜻이 아니다.

숨김 입력도 프로세스 메모리·관리자 권한·단말 기록 정책까지 해결하지는 않는다. 개인 단말의 메모리/덤프 접근 통제와 계정 만료·회수 정책은 별도로 적용한다. 이 도구는 비밀번호의 모든 메모리 복사본 삭제를 보장하지 않는다.

자동 실행이 나중에 필요하면 승인된 OS 자격증명 저장소 또는 Oracle Wallet 같은 사내 표준을 우선 검토한다. 자체 암호화 파일과 소스에 넣은 복호화 키를 새로 만드는 방식은 채택하지 않는다. 현재 쉘에는 자동화용 평문 비밀번호 옵션을 제공하지 않는다.

## 4. 준비 및 실제 실행 명령

지원 환경: Bash·Python 3·JDK 21·Maven을 실행할 수 있는 개발단말. Windows CMD/PowerShell 직접 실행용이 아니다. 사내 승인된 셸 환경을 사용한다.

접속정보는 대화/메신저로 전달하지 말고 개발단말에서 직접 입력한다. 아래 명령에는 실제 접속정보가 없다.

```sh
# 프로젝트 루트에서 실행. 의존성은 사내 Maven 저장소 정책에 맞춰 준비한다.
mvn -DskipTests package

# private 디렉터리는 저장소 밖에 만든다. HOME 값을 변경하지 않는다.
install -d -m 700 "$HOME/.config/mobilecert-test"

# 빈 설정 템플릿만 생성한다. 기존 파일은 덮어쓰지 않는다.
tools/tests/verify-dev-oracle.sh init-config \
  --config "$HOME/.config/mobilecert-test/development.json"
```

생성한 JSON의 `CHANGE_ME`만 개발단말 편집기에서 수정한다. 파일에 계정·비밀번호를 추가하면 도구가 거부한다. 호스트/서비스 이름만 보고 개발 DB 여부를 판단하지 말고 DBA가 확인한 예상 식별값을 입력한다.

| 키 | 설정할 값 |
|---|---|
| `environment` | `development` 유지 |
| `jdbc_url` | DBA가 확인한 개발 전용 호스트·포트·서비스. 계정/비밀번호/URL 옵션 없음 |
| `expected_db_unique_name` | 개발 DB의 `SYS_CONTEXT('USERENV','DB_UNIQUE_NAME')` 예상값 |
| `expected_service_name` | `SYS_CONTEXT('USERENV','SERVICE_NAME')` 예상값. URL 서비스와 동일 |
| `expected_con_name` | `SYS_CONTEXT('USERENV','CON_NAME')` 예상값. DBA에게 확인 |
| `expected_db_major_version` | `19` 유지 |
| `cert_table`, `info_table` | 기존 SMS의 실제 해당 월 테이블 이름. `SMS.` 없이 대문자 이름만 입력 |

이 식별값들은 계정 비밀번호가 아니지만 내부 DB 정보이므로 외부에 공유하지 않는다. 설정 값 자체가 자동 승인 목록이 되는 것은 아니다. 올바른 개발 DB라는 확인은 사내 inventory/DBA 정보를 기준으로 한다.

```sh
# 형식·권한만 검사. 네트워크 연결도, 비밀번호 입력도 없다.
tools/tests/verify-dev-oracle.sh check-config \
  --config "$HOME/.config/mobilecert-test/development.json"

# 여기서만 DB에 접속한다. 계정과 비밀번호가 각각 숨김 입력으로 요청된다.
tools/tests/verify-dev-oracle.sh preflight \
  --config "$HOME/.config/mobilecert-test/development.json"
```

점검 순서는 `연결 → READ ONLY 트랜잭션 → 예상 DB/서비스/컨테이너/19c 확인 → 기존 SMS 객체 컬럼 확인 → rollback/close`다.
`WHERE 1=0`으로 컬럼 접근 가능 여부를 검사하고 업무 행을 읽지 않는다. 시퀀스는 메타데이터로만 확인하며 번호를 소비하지 않는다. 접속 및 쿼리에는 시간 제한을 두고, Java 점검 프로세스는 45초 제한을 둔다.

결과는 화면에 표시된 `target/test-runs/dev-oracle-<임의값>/index.html` 및 같은 위치 `summary.json`이다. 실행마다 다른 디렉터리를 써서 이전 PASS와 혼동하지 않게 한다. 설정/입력 단계에서 중단되면 DB 보고서는 생성되지 않는다.

종료 코드: `0` 점검 성공, `1` DB 점검 실패, `2` 설정·입력·실행환경 오류. 이 쉘과 Maven/기존 검증 쉘을 같은 체크아웃에서 동시에 실행하지 않는다.

실패 시 원문 접속정보를 로그로 켜서 공유하지 않는다. 네트워크/암호화/계정 오류는 Oracle 오류번호로 DBA와 확인한다. 객체 오류는 해당 계정의 조회 권한과 실제 월별 테이블/컬럼을 확인한다. 신원 불일치는 접속 설정을 재확인하며 검사 조건을 삭제하지 않는다.

## 5. 기존 JUnit 실행

아래 명령은 개발단말에서도 실행 가능하지만 실제 개발 DB에 접속하는 시험은 아니다. 각각 순차 실행하고 실패 종료 코드를 유지한다.

```sh
tools/tests/verify-mobilecert.sh regression
tools/tests/verify-mobilecert.sh readiness
tools/tests/verify-mobilecert.sh coverage
```

정상/호환성 회귀와 기존 결함의 기대 동작 검증은 별도 결과다. 회귀가 성공해도 readiness 실패가 있으면 릴리스 준비 완료로 보지 않는다. JaCoCo 결과는 `target/site/jacoco/jacoco.xml`이며 사내 SonarQube 분석에 연결한다. 실제 사내 Quality Profile을 실행하기 전까지 Sonar 통과를 주장하지 않는다.

후속 로그 정비 작업 트리에는 `LogSafetyTest`, `ServerLoggingTest`, `ProviderLoggingTest`, `DaoLoggingTest`가 추가됐다. 별도 appender로 실제 출력 레벨·합성 민감값 미노출·ThreadLocal 요청 ID 정리·전문 바이트 불변을 확인한다. `safe-logging`에서 회귀 **42개 모두 통과**했다(기존 22개 + 로그 검증 20개). 메인 통합 후 coverage 실행도 42개 모두 통과했다(줄 39.6%, 분기 27.5%). readiness는 기존 장애 사례 10개 실패, 패키징은 성공했다. 이 시험들은 개발 DB에 접속하지 않는다.

`verify-oracle.sh`는 Docker 전용이다. 개발 Oracle 주소를 넣기 위해 loopback 검사나 PDB 소유권 검사를 제거하지 않는다. 기존 Oracle JUnit은 로컬 합성 스키마·실패 유도용 제약조건에 의존하므로 개발 SMS에 그대로 실행하지 않는다.

## 6. 다음 구현: 실제 인증 흐름 실행기

구성은 `MCI 합성 요청 클라이언트 → 실제 모바일인증 서버 → 기존 개발 SMS + 로컬 KCB 모의 서버`다. 서버의 인증 업무 코드는 그대로 실행한다. 기동용 테스트 디렉터리와 설정을 따로 만들고 운영 설정은 읽지 않는다.

- MCI 쪽은 8자리 바이트 길이, KCB 쪽은 4자리 바이트 길이를 가진 TCP 전문이다. 실제 고정 필드·EUC-KR·패딩을 검증한다.
- STEP1 응답의 거래번호를 STEP2에서 사용한다. 모의 서버는 거래별 상태를 유지한다. 요청을 검사하지 않고 무조건 성공을 반환하는 방식은 피한다.
- `Gateway`의 STEP1/STEP2 강제 응답 옵션은 꺼야 한다. 이 옵션은 외부 통신 후 응답을 덮어쓰며, 통신 자체를 차단하지 않는다.
- KCB 대상은 로컬 모의 서버로 고정한다. KCB 테스트 서버 검증은 접속 대상/목적을 구분한 별도 실행으로 만든다. 기본값으로 외부 KCB를 호출하지 않는다.
- 월별 테이블은 개발 DB의 기존 객체를 사용한다. 월 경계 STEP1/STEP2는 전월 거래 조회 동작을 별도 검토하며 공용 서버 시간을 변경하지 않는다.
- 결과 비교는 최종 응답, 해당 거래의 DB 결과, 모의 KCB 수신 기록을 함께 사용한다. 개인정보·원문 전문·접속정보는 보고서에 남기지 않는다.
- 기동 실패·테스트 실패·중단 시 자신이 시작한 프로세스만 종료한다. 개발 DB/PDB/테이블은 종료 시에도 삭제하지 않는다.

전체 실행기는 `자격증명 공급 → 설정 생성 → 서버/모의 서버 기동 → JUnit 시나리오 → 보고서 → 프로세스 정리`를 담당한다. 자격증명은 테스트 전용 기동 어댑터로 메모리에 전달하는 방안을 우선 적용하고, 현행 XML에 비밀번호를 써 넣는 방식은 기본값으로 만들지 않는다. **현재 사전 점검의 숨김 입력 기능이 운영 서버 기동까지 연결된 것은 아니다.**

시나리오: 정상 STEP1/STEP2, 잘못된 인증번호, 만료/횟수 초과, 중복/동시 요청, 전문 분할/EOF/잘못된 길이, KCB 응답 지연, 접수 후 응답 유실, 자원 반환, 종료 중 요청 처리. DB 실패는 격리 시험으로 보완한다. 접수 후 응답 유실을 일반 실패와 구분하고 자동 재발송은 하지 않는다.

기대 결과·전문은 확보한 KCB 규격/승인된 합성 샘플을 기준으로 확정한다. 로컬 모의 서버 성공은 KCB 공식 전문 적합성이나 통신사 실제 발송의 증거가 아니다. KCB가 제공하는 테스트 범위는 실제 계약/규격으로 확인한다.

## 7. 성능·소나큐브·로그 검증

부하 결과는 개발단말 성능 측정과 향후 운영급 서버 성능 측정을 구분한다. 공용 개발 Oracle에 대한 부하 상한·시간·중단 기준을 정한 뒤 단계적으로 올린다. 임의의 100 TPS를 운영 보장치로 해석하지 않는다.

요청량과 완료량을 각각 기록하고, 인증 완료 건수와 STEP1/STEP2 요청 TPS를 구분한다. p95/p99 응답시간, 시스템 실패율, 업무 거절률, 스레드/소켓/힙, Hikari active/idle/pending, DB 대기와 부하 종료 후 회복을 관측한다. KCB가 느린 시나리오도 포함한다.

현재 요청마다 플랫폼 스레드가 생성되는 구조다. 전체 시험으로 기준 동작을 확보한 뒤 최대 동시 처리·대기열·거절 정책을 정하고 보완한다. 단순히 스레드 수를 크게 설정하거나 가상 스레드로 바꾸는 것을 용량 검증으로 대신하지 않는다.

로그 개선은 [구현 및 검증 기준](logging-improvement.md)에 정리했다. `safe-logging` 작업 트리에서 운영 소스 16개 파일에 레벨 분류, 원문 전문·SQL·민감값 출력 제거, 정제된 예외 API, 서버 생성 요청 ID를 반영했다. 로그 캡처 시험을 포함한 회귀 42개가 통과했고 메인 통합 후 coverage에서도 42개가 통과했다. SQL·반환값·Hikari 설정·타임아웃·기존 업무/동시성 결함은 이번 로그 변경으로 수정하지 않았다.

`mci.responseSent`는 응답 전송 완료이며 본인인증 성공을 의미하지 않는다. LGU 라우팅 파일 실패는 기존 KCB fallback을 유지하면서 JVM 최초 1회만 WARN, 이후 DEBUG로 기록한다. `Log.write()`는 수동 도구의 기존 ERROR 동작을 위한 호환 API로 남고 활성 서비스는 새 레벨 API를 사용한다.

실제 외부 Log4j2 배포 설정은 제공되지 않았다. 운영 반영 전 logger와 appender의 INFO/WARN 임계값, 변경된 메시지/요청 ID에 대한 알람 parser, 인코딩·보관·출력량을 확인한다. Hikari의 SLF4J→JUL 경로는 정제 대상 밖이며 DEBUG 설정 덤프를 피한다. 애플리케이션 로그 캡처 성공만으로 전체 프로세스 로그의 민감값 미출력을 보장하지 않는다.

## 8. Vault 전환 지점

목표는 인증 업무 코드가 비밀 저장소에 직접 의존하지 않도록 자격증명 공급을 분리하는 것이다. 현재는 대화형 입력이며, Vault 연동은 미구현이다.

Vault Agent 파일 전달 방식을 채택하면 승인된 외부 경로, 파일 0600·디렉터리 0700, `error_on_missing_key=true`, `backup=false` 등을 명시하고 파일/토큰을 저장소·로그에서 제외한다. Agent의 템플릿 권한 기본값을 그대로 보안 기본값으로 간주하지 않는다. [HashiCorp Vault Agent 템플릿 문서](https://developer.hashicorp.com/vault/docs/agent-and-proxy/agent/template)

장기 실행 Hikari 풀은 Vault가 파일을 갱신했다고 자동으로 새 비밀번호를 사용하지 않는다. static/dynamic 자격증명 선택, lease/갱신/만료, 풀 재생성 또는 통제된 재시작, 장애 시 동작을 함께 설계한다. 비밀번호 파일을 읽는 기능만으로 Vault 연동 완료로 보고하지 않는다.

## 9. 작업별 검증 기록

### 개발 Oracle 사전 점검 도구

- 담당: Codex 및 읽기 전용 로그 검토/Java 점검기 구현 서브에이전트.
- Worktree: `worktrees/dev-test-guide`, 브랜치 `codex/mobilecert-dev-test-guide`.
- 실제 개발 Oracle/KCB/내부 MCI 접속: 수행하지 않음. 실제 주소·계정·비밀번호는 요청하거나 수집하지 않음.
- 검증: 쉘 문법·도움말·설정 생성/거부 확인, Python 안전성 11개, Java 잘못된 입력 13개·읽기 전용 SQL/정리 10개·실행기→Java 통합 3개 성공(자동 오프라인 시험 총 37개). Java 21 컴파일 경고 없음. 실제 DB 접속 결과가 아님.
- 실제 전체 인증 흐름·부하는 미구현이다. 운영 로그 수정은 이후 `safe-logging` 작업 트리에 구현했으며 아래에 상태를 구분한다.
- Qwen 3.8 Max 호출 없음. Orca 연결 도구가 없어 로컬 계획만 기록하며 실제 Orca Task ID는 없음.

새 도구 자체의 안전성 검증은 DB 없이 반복할 수 있다.

```sh
python3 -I tools/tests/test_development_oracle.py
python3 -I tools/tests/test_development_probe.py
```

두 번째 명령은 JDK 21로 점검기와 가짜 JDBC 드라이버를 시스템 임시 디렉터리에 컴파일한다. 가짜 드라이버는 `tools/tests/fixtures`의 오프라인 시험 전용이며 실제 `target/lib`에 넣거나 배포하면 안 된다. 실제 개발 접속 명령은 현재 POM에 지정된 ojdbc11 JAR만 선택한다.

### 후속 운영 로그 정비

- 담당: Codex 및 운영 로그 구현·로그 캡처 시험·읽기 전용 검토 서브에이전트.
- Worktree: `worktrees/safe-logging`. 운영 로그 코드 구현·회귀 검증 및 메인 작업 트리 통합 완료.
- 변경 범위: 운영 소스 16개 파일의 로그와 요청 추적. 인증 업무·SQL·풀 설정·타임아웃은 유지했다.
- 회귀 결과: **42개 모두 통과**(기존 22개 + 로그 검증 20개). 레벨/정제된 예외/요청 ID/합성 개인정보 미출력 및 기존 전문 회귀를 포함한다. 메인 coverage도 42개 통과했으며 줄 39.6%, 분기 27.5%다. readiness는 기존 장애 사례 10개 실패, 패키징은 성공했다.
- 별도 JDK 21 로그 변경 전/후 비교: Provider 6개 경로 6,038바이트 동일, Protocol 13개 통과. 기존 Java 6/8 런타임 실행물 비교는 아니다.
- 실제 개발 Oracle/KCB/내부 MCI 접속, 실제 배포 로그 설정 검증·부하 시험은 수행하지 않았다. 개발 SMS 도구는 여전히 읽기 전용 사전 점검이며 전체 인증 실행기가 아니다.
- Qwen 3.8 Max 호출 없음.
